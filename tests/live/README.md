# ライブサイト検証

サイトのHTMLをfixtureとして保存せず、実行時のページをChromiumで描画し、本番ビルドのContent Script → 日付抽出 → サイドパネル表示を通して検証する。AIは無効。対象イベントの開始・終了日時が候補に含まれることを確認する。全候補の正確さや、余分な候補が一切ないことまでは保証しない。

## 実行するタイミング

main宛てのPRがマージされたときに、登録済みの全サイトを1回ずつ自動検証する。PRの作成・更新中には起動しない。マージせずに閉じた場合はジョブをスキップし、mainへの直接pushや他のブランチへのマージでも検証しない。

手動実行も残す。GitHub Actionsの「Live event sites」から「Run workflow」を選び、ブランチは `main`、通常は `sites: all` にする。ストア更新前にはアップロード対象コミットでの検証結果を確認し、必要な場合だけ再実行する。main以外の手動実行はスキップする。

トリガーは `pull_request` の `closed`（対象main）と `workflow_dispatch`。ジョブの条件でもマージ済みかを確認する。マージ時は入力欄がないため `sites` を `all` に補う。scheduleは未設定で、週次実行は運用が安定してから明示的に追加する。

このワークフローはmainにマージ後に利用できる。テスト開始時のコミットSHAをCIのレポートに記録する。テスト後にコードを変更した場合、その結果を変更後の配布物の検証結果として扱わない。

CIはPlaywright公式Dockerイメージを使い、毎回のOS依存・ブラウザのインストールを省く。非root実行とChromiumサンドボックスを有効にし、外部サイトに接続する前にローカルfixtureで起動・抽出・失敗分類を確認する。イメージ取得・npm依存・ビルド・ローカル確認・ライブ検証は別工程として表示する。[コンテナの構成と更新手順](../../scripts/ci/README.md)も参照。

## ローカルでの実行

```sh
npm ci
npx playwright install chromium
npm run build
npm run test:live
```

特定サイトだけ再確認する場合：

```sh
LIVE_SITES=connpass,meetup npm run test:live
# Lumaだけを確認する場合
LIVE_SITES=luma npm run test:live
```

未登録のIDはブラウザを開く前に拒否する。テストはビルド済みの `.output/chrome-mv3` を利用するため、必ず先にビルドする。実行中のブランチ切り替え・ビルドは避ける。各ケースはビルドを一時ディレクトリへコピーして利用し、終了時に削除する。

通常の `npm test`、`npm run check`、`npm run test:e2e` はライブサイトに接続しない。`tests/e2e/live-harness.spec.js` はローカルのHTTPサーバーだけを使い、検証処理の成功・日時不一致・403・429・404・認証画面・別ページ・別オリジンへの移動を確認する。

## 負荷と保存データ

- 1サイトにつき登録したイベント詳細1ページだけを開く。一覧巡回やイベントの自動探索はしない。
- 1 workerで直列に実行し、各ケースの後に2秒空ける。自動リトライ・繰り返しは0回。CIの同時実行も抑止する。
- 画像・動画・フォントは取得を抑止し、描画・動的表示に必要なCSS・JavaScriptは維持する。1ページの表示には複数のサブリソース取得やリダイレクトがあるため、HTTPリクエストが1回だけになるという意味ではない。
- ログインやCAPTCHAの操作、アクセス制限の回避はしない。GitHubの実行環境からだけ拒否される場合も、合格扱いにしない。
- 言語は `ja-JP`、タイムゾーンは `Asia/Tokyo`、画面は1280×900に固定する。現在の日付は固定しない。
- 本文とJSON-LDの変化が750ms落ち着き、対象イベントの識別文が見つかってから1回スキャンする。待ち時間は最大15秒。期待日時や抽出成功を読み込み待ちの条件には使わない。
- `readySelector` があるサイトでは、その領域が表示され、空でない本文が入るまで待つ。Peatixは文書タイトル・ヘッダ・フッタが本文より先に完成するため、イベント説明領域 `#field-event-description` を指定している。領域が描画されなければ `PAGE_NOT_READY`、描画後に期待日時が見つからなければ `DATE_MISMATCH` とする。
- HTML・DOM・本文・スクリーンショット・動画・Playwright traceはレポートとして保存しない。一時ブラウザプロファイルは終了時に削除する。
- レポートには対象URL、日時、HTTP状態、分類、所要時間、検証段階、候補の日時だけを記録する。CIではJSONとMarkdownだけを14日間保存する。

本番manifestは変更しない。ツールバーのactiveTab付与を自動操作できないため、一時コピーだけに対象URLのオリジンのhost権限を追加する。別オリジンへの移動は対象変更として失敗させる。権限の自動実行範囲を拡張したり、別サイトを探索して代替イベントを探したりしない。

## 結果の読み方

`test-results/live/report.json` に候補と期待値、`summary.md` に一覧を出力する。CIでは実行サマリーとArtifactで確認する。通常のE2Eを後から実行すると `test-results` が初期化されるため、ローカルで結果を残したい場合は先に別の場所へコピーする。

| 分類                              | 意味・確認すること                                                                                 |
| --------------------------------- | -------------------------------------------------------------------------------------------------- |
| `PASS`                            | 同じ候補の開始・終了日時が、手動確認した期待値と一致                                               |
| `DATE_MISMATCH`                   | 対象ページは開けたが期待日時が候補にない。ページ内容を確認し、抽出の退行と開催日時変更を切り分ける |
| `ACCESS_BLOCKED` / `RATE_LIMITED` | 認証・bot対策・403・429など。短時間に繰り返さず、手動で確認する                                    |
| `PAGE_MISSING`                    | 404・410。公開された別の代表イベントへ登録内容を更新する                                           |
| `NETWORK_ERROR` / `HTTP_ERROR`    | 通信失敗・タイムアウト・サーバーエラー。抽出の失敗とは別に扱う                                     |
| `TARGET_CHANGED`                  | 別オリジンへの移動や、登録したイベントの識別文を確認できない                                       |
| `PAGE_NOT_READY`                  | 本文が落ち着かない、必要な表示を待てない。動的表示を手動確認する                                   |
| `HARNESS_ERROR`                   | ビルド・拡張の起動・スキャン操作など検証環境の問題。JSONの `phase` を確認する                      |
| `NOT_RUN`                         | 実行前のエラーや中断など。検証したものとして扱わない                                               |

エラーを自動的にskipして緑にしない。サーバーがHTTP 202を返しても、対象ページを正常に描画して日時を抽出できれば合格にする。本文の「ログインしてください」という案内だけでは認証画面と判定しない。

## サイトを追加・更新する

`sites.js` に次の形式で追加する。既存の公開ページをブラウザで確認してURLと日時を登録し、抽出結果から期待値を自動生成しない。

```js
{
  id: "example", // 一意な英小文字・数字・ハイフン
  name: "サービス名",
  reviewedOn: "2026-10-28", // 画面の日時を確認した日本時間の日付
  url: "https://events.example.com/event/123",
  identity: "対象イベントの識別に使えるタイトルの一部",
  expected: {
    start: "2026-12-01T18:00:00+09:00",
    end: "2026-12-01T20:00:00+09:00",
  },
  // 必要なときだけ、本文領域が表示され、テキストが入るのを待つ。
  // 期待日時や抽出結果に依存せず、レイアウトに依存しにくいID等を選ぶ。
  // readySelector: "#event-description",
}
```

- データを追加すればテストケースも増える。CIのsites入力は任意の登録IDを受け付けるので、ワークフローのロジック変更は不要（入力欄の説明にあるID一覧は必要に応じて更新）。
- 現在は開始・終了時刻が明記されたイベントを対象とする。終日予定は通常のローカルテストで検証している。ライブケースでの終日対応は別途追加する。
- CSSの見た目や固定件数には依存しない。対象イベントの識別文は、文書タイトルまたは描画済み本文で確認する。文書タイトルだけが先に読み込まれるサイトでは `readySelector` で本文の描画も確認する。
- 終了済みイベントでもページが残っていれば利用できる。公開終了・日程変更では、人が確認してURLと期待値を更新する。テストを通すためだけに期待値を抽出結果へ合わせない。
- 年がない表記を現行の年として補う挙動も含めて検証するため、年越し後に失敗するケースは実ページを再確認する。自動的に期待年を更新しない。
- 最新イベントを自動選定する方式は、正解日時の独立した判定や追加アクセスが必要になるため、現段階では採用しない。

## サンプルを見直す

ストア公開前に `npm run check:live-samples` を実行する。Node.jsだけで動き、ビルド・追加パッケージ・外部アクセスは不要。全登録サイトについて、以下の早い方を見直し時期として表示する。

- 開催終了日から30日後
- `reviewedOn`（最終確認日）から90日後

日本時間の暦日で判定し、該当日の0時から見直し対象になる。これは更新の目安であり、ページが消失しない期限ではない。消失・対象変更などの失敗は期限前でも調査する。

既存のライブWFにも同じ一覧をサマリー表示する。古さだけでは失敗・スキップにせず、CLIも終了コード0とする。確認日の欠落・不正・未来日など、登録データの不備はエラー。WFの実行頻度は変えず、定期探索・自動差し替え・Issue自動作成は行わない。

### 更新の手順

1. 見直し対象、または明示的に指定されたサイトを選ぶ。失敗がきっかけなら、先にレポートを読み、ページ消失・開催日時変更・アクセス制限・抽出や読み込み待ちの不具合を切り分ける。失敗を消すためだけに対象を交換しない。
2. 対象サービスの公開一覧や検索から、開始・終了日時と年・タイムゾーンを確認できる詳細ページを選ぶ。可能なら1〜3か月先のイベントを優先するが、明確な日時と既存ケースの代表性（言語、本文・構造化データ、動的表示）を優先する。1サイトにつき一覧または検索1回と、詳細ページ最大3件を目安にし、連続巡回しない。見つからなければ既存データを保持して報告する。401/403/429・認証・CAPTCHAではそのサイトの探索を止め、回避や自動再試行をしない。
3. 描画された画面の開始・終了日時を、拡張の抽出結果と独立して読み取る。期待値を抽出器から生成しない。本文と構造化データが食い違う、終了時刻・年・時差が確定できない場合は推測で登録しない。
4. `sites.js` のURL・識別文・期待日時・`reviewedOn`を更新する。必要な場合は本文の`readySelector`も見直す。`reviewedOn`は実際に画面を確認した日とし、テストに通っただけで更新しない。古いイベントを確認し直しても、開催終了30日の目安は延長されない。
5. `npm run check` を実行し、`LIVE_SITES=<更新したIDのカンマ区切り> npm run test:live` で変更対象だけ1回検証する。失敗したら分類と結果を報告し、自動リトライや期待値のすり替えをしない。既存のHTMLや本文を保存しない方針は維持する。
6. 更新PRに旧・新URL、画面で確認した開始・終了日時と時差、確認日、更新理由、検証結果を記載する。変更差分から独立した確認の根拠を追えるようにし、PRのマージやWF再実行は依頼の範囲に従う。マージ後は通常の全サイトWFが実行される。

この手順は手動でも使える。Codexに更新用Skill `sche10le-refresh-live-samples` を導入した環境では「`$sche10le-refresh-live-samples` で見直し対象を更新して」と依頼できる。Skill本体はユーザーのスキルディレクトリに置き、運用ルールの正本はこの節とする。Skillの実行自体はスケジュールされない。

初期6ケースは2026年10月27日に確認。connpass・Peatix・こくちーずプロは本文、Doorkeeper・TECH PLAY・Meetupは構造化データ経由の候補も検証できる代表ページを登録している。ただし合否は経路ではなく期待日時の一致で決める。
